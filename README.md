# Sbor — Telegram-бот для сбора заявок

Готовая основа для малого бизнеса. Клиенты заполняют форму внутри Telegram, владелец получает уведомления и ведёт заявки через Telegram-админ-панель.

## Возможности

- Пошаговая форма: услуга, имя, способ связи, описание, бюджет и срок.
- Дополнительные вопросы, настраиваемые владельцем.
- Уведомления администраторам с номером заявки и фиксацией неудачной доставки.
- Повторная отправка недоставленных уведомлений только администраторам, которым оно не дошло.
- Статусы: новая, в работе, выполнена, отменена.
- Фильтр по статусу, страницы по 10 заявок и поиск по номеру, имени или контакту.
- Статистика и экспорт заявок в CSV с защитой от выполнения формул в табличных редакторах.
- Настройка названия компании, приветствия, контактного текста, услуг и вопросов без изменения кода.
- SQLite, создание таблиц и миграция старой схемы без потери заявок.
- Стартовая и ежедневная автоматическая резервная копия SQLite с ограничением числа снимков.
- Создание и скачивание резервной копии через админку, проверка целостности и восстановление с автоматическим снимком текущего состояния.
- Восстановление из загруженного файла SQLite размером до 19 МБ — например, после переезда на новый хостинг.
- Отдельный бот, токен и база данных для каждого покупателя.

## Быстрый запуск

Требуется Python 3.11 или новее.

1. Создайте Telegram-бота через @BotFather и скопируйте токен.
2. Скопируйте файл .env.example в .env и заполните BOT_TOKEN и ADMIN_IDS. ADMIN_IDS — числовой Telegram ID владельца или администраторов; несколько ID разделяются запятыми.
3. Установите зависимости:

    python -m pip install -r requirements.txt

4. Запустите:

    python main.py

5. Откройте диалог с ботом, отправьте /start. Для панели управления используйте /admin.

Приложение загружает переменные окружения из .env. Не добавляйте .env или настоящий токен в GitHub.

## Подготовка администраторов и уведомлений

**Каждый ID в ADMIN_IDS должен сначала открыть личный чат с ботом и отправить /start.** Telegram не позволяет боту начать личную переписку с пользователем, который её ещё не активировал.

В админ-панели откройте «Проверка уведомлений». Там показываются заявки с недоставленными или ещё не проверенными уведомлениями. Откройте заявку, чтобы повторить отправку. При повторе сообщение направляется только тем администраторам, которым оно не доставилось на предыдущих попытках.

Если уведомление не доставлено никому, это не отменяет сохранение заявки: заявка остаётся в базе, а её ошибка доставки появляется в админ-панели.

## Запуск через Docker

    docker build -t sbor-bot .
    docker run --restart unless-stopped \
      -e BOT_TOKEN='ВАШ_ТОКЕН' \
      -e ADMIN_IDS='ВАШ_TELEGRAM_ID' \
      -e DATABASE_PATH='/app/data/sbor.sqlite3' \
      -v sbor-data:/app/data \
      sbor-bot

Для Amvera или другого хостинга задайте BOT_TOKEN и ADMIN_IDS в настройках приложения. Укажите DATABASE_PATH внутри постоянного тома/диска хостинга, чтобы заявки не терялись при пересборке или повторном развёртывании. Для long polling запускайте только один экземпляр одного и того же токена.

## Админ-панель

Команда /admin доступна только пользователям из ADMIN_IDS и только в личном чате с ботом.

- **Новые / Все / В работе / Выполненные / Отменённые** — отдельные фильтры и постраничный просмотр по 10 заявок.
- **Поиск** — укажите номер заявки (например, #24), имя или контакт клиента. В выдаче показывается до 10 совпадений.
- **Статистика** — общее количество, количество по статусам и число проблем с доставкой уведомлений.
- **Экспорт CSV** — скачать таблицу в личном чате с ботом. Значения, похожие на формулы, безопасно преобразуются в текст.
- **Проверка уведомлений** — показывает неудачные доставки; можно отправить повторно.
- **Создать копию / Резервные копии** — создать и выгрузить файл базы, выбрать локальную копию или загрузить проверенный файл для восстановления.
- **Настройки** — изменить название, тексты, услуги и дополнительные вопросы. В списках указывайте по одному пункту на строку; дефис очищает список.

Настройки, внесённые через панель, хранятся в базе данных. Изменения в config.json применяются как начальные значения только при первом создании соответствующих настроек в новой базе.

## Резервное копирование и восстановление

После инициализации базы бот создаёт стартовую резервную копию, затем делает копию каждые BACKUP_INTERVAL_HOURS часов (по умолчанию 24). Копии создаются через SQLite Backup API, поэтому снимок согласован с работающей базой, включая изменения в WAL.

Настройки окружения:

- **BACKUP_DIRECTORY** — каталог резервных копий. По умолчанию это папка backups рядом с файлом базы. Она должна находиться на постоянном диске хостинга.
- **BACKUP_RETENTION** — сколько последних копий хранить (по умолчанию 10, допустимо 1–100).
- **BACKUP_INTERVAL_HOURS** — интервал автоматического копирования в часах (по умолчанию 24, допустимо 1–168).

### Создать внешнюю копию

В админ-панели нажмите «Создать копию». Бот создаст файл базы, проверит его целостность, сохранит на сервере и отправит файл администратору в личные сообщения. Скачайте его на устройство или в другое независимое хранилище. Резервная копия на том же диске не защитит от потери всего хостинга.

### Восстановить копию

1. Откройте «Резервные копии» и выберите дату нужной копии либо нажмите «Загрузить копию с устройства».
2. При загрузке допускаются SQLite-файлы с расширением .sqlite3, .sqlite или .db размером до 19 МБ. Файл проверяется до того, как появится возможность его восстановить.
3. Нажмите «Да, восстановить эту копию» только после проверки даты и имени файла.

Перед восстановлением бот автоматически создаёт отдельный снимок текущего состояния. После восстановления прежние заявки и настройки возвращаются к состоянию выбранного снимка; данные, созданные позже, не входят в активную базу. Перед восстановлением всегда внимательно проверяйте дату копии.

Резервные копии содержат контакты клиентов и другие данные из заявок. Не пересылайте их посторонним и храните в защищённом месте. Ошибки создания копий записываются в журнал приложения; если постоянный диск хостинга недоступен, бот продолжает работать, но резервное копирование может не сработать.

## Тесты

GitHub Actions выполняет проверку синтаксиса Python и тесты базы данных/функций безопасности. Покрыты: сохранение заявки, статусы, страницы и поиск, безопасный экспорт ячеек CSV, уведомления и миграция старой схемы базы.

## Важные замечания перед продажей

- Для каждого клиента создавайте отдельного Telegram-бота, отдельный токен и отдельную базу/том. Не используйте одну базу для разных покупателей.
- Перед передачей замените примеры текстов и список услуг под конкретную компанию.
- Владелец бота отвечает за законность сбора и хранения персональных данных и за публикацию нужной ему политики конфиденциальности.
- Токен бота — секрет. Не публикуйте его в коде или коммитах. При утечке перевыпустите токен через BotFather.
- Первая версия использует Telegram-админ-панель; отдельной веб-CRM в ней нет.
- Резервные копии по умолчанию хранятся на том же постоянном диске; для защиты от полного отказа хостинга скачивайте файлы, которые бот отправляет после ручного создания копии.
- Автоматическое удаление старых заявок по политике хранения данных пока не входит в эту версию.

## Структура

- main.py — команды, клиентская форма, админ-панель, поиск и уведомления.
- database.py — хранение заявок, настроек и состояния доставки в SQLite.
- keyboards.py — клиентские и административные клавиатуры.
- safety.py — проверка доступа и безопасная обработка значений CSV.
- config.py и config.json — переменные окружения и начальные значения.
- Dockerfile — контейнерный запуск.
